# 슬라이스 2b: 레벨업 3택 + 증강 시스템 + 체력바 설계

- 상태: 승인됨 (브레인스토밍 완료, 구현 계획 대기)
- 선행 문서: [슬라이스 1 코어 아키텍처](2026-08-19-core-architecture-design.md),
  [슬라이스 2a 캐릭터 선택 + 간장새우](2026-08-19-slice2a-character-select-and-shrimp-design.md)
- 기획서 압축본: [CLAUDE.md](../../../CLAUDE.md)
- 날짜: 2026-08-19

## 배경

슬라이스 2a까지 캐릭터 2종을 골라 플레이할 수 있게 되었지만, 무기 레벨이
인스펙터 고정값이라 애써 입력한 Lv1~4 수치 테이블이 전혀 쓰이지 않고 있다.
경험치도 쌓이기만 하고 아무 일도 일어나지 않는다. 슬라이스 1에서 만든
`StatSystem`은 아직 아무도 사용하지 않는다.

이 슬라이스는 뱀파이어 서바이벌류의 핵심 재미인 "처치 → 레벨업 → 선택 → 강해짐"
루프를 완성한다. 함께 요청된 두 가지(플레이어 체력 표시, 잡몹 2종화)도 포함한다.

## 기획서 정정 사항

**`CLAUDE.md`의 "중형몹 = 캘리포니아롤" 기술은 잘못되었다.** 아트 확인 결과 둘은
별개의 몬스터다.

| 시트 | 크기 | 프레임 규격 | 분류 |
|---|---|---|---|
| `new 몬스터-Sheet.png` | 250×50 | 50×50 × 5 | 잡몹 #1 (검은 초밥 병사) |
| `캘리포니아롤-Sheet.png` | 250×50 | 50×50 × 5 | **잡몹 #2** |
| `중형몹 이동-Sheet.png` | 500×100 | 100×100 × 5 | 중형몹 (별개 몬스터) |

캘리포니아롤은 잡몹과 프레임 규격이 완전히 동일하고, 중형몹은 2배 크기의 다른
그림이다. 따라서 **잡몹은 2종**이며, 중형몹은 자기 아트를 가진 별도 몬스터로
이후 웨이브 타임라인 슬라이스에서 다룬다.

이 슬라이스 구현 시 `CLAUDE.md`의 몬스터 표도 함께 정정한다.

## 결정 사항 요약

| 항목 | 결정 |
|---|---|
| 3택 내용 | 증강 10종 + 무기 강화(Lv1→4)를 한 풀에 섞음 |
| 팝업 중 게임 | `Time.timeScale = 0`으로 일시정지 |
| 레벨업 필요 XP | 인스펙터 노출 공식(기본값 + 레벨당 증가분), 플레이테스트로 튜닝 |
| 스탯 적용 | `PlayerStats`가 `StatSystem`을 소유하고 모든 소비처가 여기서 읽음 |
| 잡몹 2종 스탯 | 살짝 차등 (캘리포니아롤을 느리고 단단하게) |
| 체력 표시 | 캐릭터 발밑 체력바 (World Space Canvas) |

## 접근법 비교: 스탯 적용 경로 (승인됨: A안)

현재 게임플레이 코드는 값을 직접 읽는다 — `PlayerController`는
`characterData.baseMoveSpeed`를, `PlayerHealth`는 `characterData.baseMaxHealth`를,
`WeaponBase`는 `CurrentStats.damage/cooldown/range`를 읽는다. 증강이 효과를
내려면 이 경로를 바꿔야 한다.

| 안 | 설명 | 채택 |
|---|---|---|
| A. `PlayerStats`가 `StatSystem` 소유 | 모든 소비처가 여기서 값을 읽는다 | **채택** |
| B. 증강이 `CharacterData`를 직접 수정 | — | 기각 (아래 참고) |
| C. 각 시스템이 자기 modifier 관리 | — | 기각 |

**B안이 위험한 이유(반드시 피할 것):** `CharacterData`는 ScriptableObject이므로
에디터 플레이 중의 수정이 에셋 파일에 영구 저장된다. 한 판 하고 나면 다음 판의
시작 체력이 이전 판에서 얻은 증강만큼 올라간 채로 시작하고, 그 변경이 프로젝트
파일에 남는다. 세이브 없는 원런 구조와 정면으로 충돌한다.

**C안이 기각된 이유:** 캡 클램프가 여러 곳에 흩어지면 "방어력 100% = 무적" 같은
조합 사고를 막기 어렵다. 기획서가 "공통 StatSystem을 통해 한 곳에서 클램프"를
명시적으로 요구한다.

## 아키텍처

### PlayerStats — 스탯 배관의 중심

플레이어 프리팹에 붙는 컴포넌트로 `StatSystem` 인스턴스를 소유한다.
`CharacterData`로 초기값을 세팅하고, 증강은 여기에 modifier를 추가한다.

스탯 성격에 따라 값 모델을 둘로 나눈다.

| 종류 | 스탯 | base | 의미 |
|---|---|---|---|
| 절대값 | `MoveSpeed`, `MaxHealth` | `CharacterData`의 값 | 그대로 사용 |
| 배율 | `AttackDamage`, `AttackSpeed`, `AttackRange` | `1.0` | 무기가 테이블 값에 곱함 |
| 비율 | `Armor`, `ExpGain`, `Regen`, `MagnetRange` | 0 또는 기본 반경 | 각 소비처가 해석 |
| 횟수 | `Revive` | 0 | 남은 부활 횟수 |

이 모델은 기획서의 단위 표기(공격력 "증가율 +200%", 공격속도 "쿨타임 감소율
-50%")와 그대로 맞아떨어진다.

### 소비처 변경

| 컴포넌트 | 변경 |
|---|---|
| `PlayerController` | 이동속도를 `PlayerStats`에서 읽음 |
| `PlayerHealth` | 최대체력을 `PlayerStats`에서 읽음, 피해에 방어력 적용, 초당 회복 틱, 사망 시 부활 처리 |
| `WeaponBase` | 데미지·쿨타임·범위에 배율 적용 |
| `GameManager` | 경험치 획득에 배율 적용 |
| `XPGem` | 고정 픽업 반경 대신 플레이어 자석 스탯 사용 |

### 레벨업 흐름

```
젬 획득 → 누적 XP 증가
  → LevelSystem이 임계값 돌파를 감지 (여러 레벨 동시 상승 가능)
  → Time.timeScale = 0, 3택 팝업 표시
  → 선택 → 적용 → 팝업 닫기
  → 대기 중인 레벨업이 남아 있으면 다시 팝업, 없으면 timeScale 복구
```

황금 젬(10XP)으로 한 번에 2~3레벨이 오를 수 있으므로 **대기 중인 레벨업을 큐로
관리**한다. 큐가 빌 때까지 게임은 멈춰 있다.

필요 경험치는 `기본값 + 레벨당 증가분 × (레벨-1)` 공식으로 계산하며, 두 값 모두
인스펙터에 노출한다. 초기값은 기본 5, 증가분 3으로 시작하고 플레이테스트로
조정한다.

### 업그레이드 선택지

두 종류를 하나의 인터페이스로 묶어 같은 풀에서 뽑는다.

```
IUpgradeOption
├─ AugmentOption        — 증강 10종 (AugmentData 에셋 기반)
└─ WeaponLevelUpOption  — 현재 무기 Lv+1
```

후보 제외 규칙:
- 무기 강화: 현재 레벨이 4(MAX)면 제외
- 증강: 누적값이 `maxCap`에 도달했으면 제외 (`AugmentData`에 `valuePerPick`과
  `maxCap`이 이미 존재한다)

후보가 3개 미만이면 있는 만큼만 표시한다. 하나도 없으면 팝업을 띄우지 않고
레벨업을 조용히 소비한다.

### 증강 10종 구현 방식

7종은 스탯 배관만으로 동작하고, 3종은 추가 훅이 필요하다.

| 증강 | 구현 위치 |
|---|---|
| 공격력 / 공격속도 / 공격범위 | `WeaponBase`가 테이블 값에 배율 적용 |
| 체력 / 이동속도 | `PlayerStats`에서 읽기만 하면 됨 |
| 방어력 | `PlayerHealth.TakeDamage`에서 `damage × (1 - armor)` |
| 경험치 획득량 | `GameManager.AddExperience`에서 배율 |
| **회복** | `PlayerHealth`에 초당 회복 틱 추가 |
| **자석** | `XPGem`이 플레이어 자석 스탯을 읽도록 변경 |
| **부활** | `PlayerHealth` 사망 시 횟수가 남아 있으면 소모하고 최대체력으로 부활 |

**하드캡 (기획서 요구사항):**
- 방어력: 0.5 (50% 감소). 이걸 넘기면 무적 조합이 생긴다.
- 공격속도: 쿨타임 배율 하한 0.5에 더해, **최소 쿨타임 절대값**을 별도로 둔다.
  배율만으로는 무기별 기본 쿨타임이 짧을 때(이나리 0.35초) 무한 연사에 가까워진다.
- 부활: 최대 1회 (MVP).

나머지 캡은 기획서의 추천 최대치를 `AugmentData` 에셋의 `maxCap`에 입력한다.

### 체력바

플레이어 자식으로 World Space Canvas를 두고 `Image`의 `Filled` 타입으로 채움
비율을 조절한다. uGUI 기본 흰색 스프라이트를 쓰므로 새 아트가 필요 없다.

비율 계산은 순수 함수로 분리해 테스트한다. 최대체력이 0이거나 현재 체력이
음수인 엣지 케이스에서도 0~1 범위를 벗어나지 않아야 한다.

몹 체력바는 이 슬라이스 범위 밖이다.

### 잡몹 2종

`EnemySpawner`가 풀 하나 대신 **풀 배열**을 갖고 매 스폰마다 무작위로 고른다.

수치는 `MonsterData` 에셋에 두어 튜닝 가능하게 한다. 제안값:

| 잡몹 | 체력 | 접촉 데미지 | 이동속도 |
|---|---|---|---|
| 검은 초밥 병사 | 12 | 5 | 2 |
| 캘리포니아롤 | 20 | 5 | 1.5 |

캘리포니아롤을 "느리고 단단한 쪽"으로 두어, 같은 잡몹이라도 섞였을 때 전투
리듬이 단조로워지지 않게 한다.

## 구현 순서

각 단계가 끝날 때마다 플레이 가능한 상태가 되도록 나눈다.

1. **스탯 배관** — `PlayerStats` 추가하고 소비처 3곳을 연결한다. 눈에 보이는
   변화는 없으며, 기존과 동일하게 동작하는지 회귀 확인만 한다.
2. **레벨업 + 3택 팝업** — 레벨 계산, 큐, 팝업 UI, 무기 강화, 스탯형 증강 7종.
3. **특수 증강 + 부가 기능** — 회복·자석·부활 3종, 체력바, 캘리포니아롤.

## 테스트 전략

기존과 동일하다. 순수 로직은 EditMode 유닛 테스트로 TDD하고, MonoBehaviour 통합
동작은 Play 모드 수동 테스트로 확인한다.

이번 슬라이스에서 유닛 테스트 대상이 되는 순수 로직:

- `LevelCurve.GetRequiredXp(level, baseXp, increment)` — 필요 경험치 공식
- `LevelCurve.CountLevelUps(totalXp, currentLevel, ...)` — 한 번에 오르는 레벨 수
- `AugmentAvailability.IsAvailable(accumulated, valuePerPick, maxCap)` — 후보 제외
- `UpgradePicker.PickDistinct(candidates, count, random)` — 중복 없이 N개 뽑기
- `HealthBarLogic.ComputeFillAmount(current, max)` — 0~1 클램프
- `ArmorLogic.ApplyArmor(damage, armor)` — 방어력 적용과 하드캡
- `CooldownLogic.ApplyAttackSpeed(baseCooldown, multiplier, minCooldown)` — 최소
  쿨타임 하드값 적용

## 에러 처리 / 엣지 케이스

- 레벨업 후보가 하나도 없으면(모든 증강 최대치 + 무기 4강) 팝업을 띄우지 않고
  레벨업을 소비한다. 빈 팝업으로 게임이 멈추면 안 된다.
- 팝업이 열린 상태에서 또 레벨업이 발생해도 큐에 쌓일 뿐, 팝업이 중복 생성되지
  않는다.
- `Time.timeScale = 0` 중에도 UI 입력은 동작해야 한다(Input System UI 모듈은
  영향받지 않는다). 팝업이 닫힐 때 반드시 `1`로 복구하며, 게임오버로 런이 끝나는
  경우에도 복구를 보장한다.
- 부활 시 체력을 최대치로 되돌리고, 주변 적을 밀어내지는 않는다(MVP).
  부활 직후 다시 즉사하는 것은 허용한다.
- 최대체력 증강을 얻으면 현재 체력도 같은 양만큼 올린다. 그러지 않으면 최대치만
  늘고 체감상 아무 일도 일어나지 않는다.
